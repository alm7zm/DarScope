# Part 2: the backend plan

How the four of us build the Spring server, and how it plugs into the React app. The brief is in [part-2-brief.md](part-2-brief.md). **Due 14 November 2026.**

The Part 1 brief says the backend "will be manually coded in part2", so **we write every line of Java and SQL ourselves**. The AI tool wrote this plan and the frontend side of the connection (the `frontend/` changes listed at the end), and it can review our code. It does not write anything in `backend/`.

## 1. How the two halves connect

```
Browser, localhost:5173                                     Spring server, localhost:8080              Database
React pages → PortfolioProvider → propertyService.js ──HTTP──► Controller → Service → Repository ──JDBC──► Supabase Postgres
                                  (fetch /api/v1/...)          (routes)     (rules)    (Spring Data)        (or H2 on your laptop)
```

- **React never touches the database.** It sends an HTTP request such as `GET /api/v1/properties/7`, and Spring answers with JSON. Only Spring talks to the database.
- **Only one frontend file talks to the server:** `frontend/src/services/propertyService.js`. Every page goes through it, which is how Part 1 was designed, so no page had to change.
- **No CORS setup is needed.** `npm run dev` forwards every `/api/...` call from port 5173 to port 8080 (`frontend/vite.config.js`). Keep Spring on its default port, **8080**. Do not copy lab 14's `server.port=3000`.
- **The contract in section 3 is what lets four people work at once.** Everyone codes against the same routes and the same JSON. If you need to change it, tell the team first, because the frontend reads exactly this shape.

## 2. Pagination in plain words

Pagination means showing a long list in pieces: page 1 is properties 1 to 10, page 2 is 11 to 20, with Previous and Next buttons. The brief wants the **server** to cut the pieces (requirement 4):

- The browser asks: `GET /api/v1/properties?page=1&size=10`. Pages are counted from 0 on the wire, so `page=1` is the second page.
- The server answers with only those 10 properties, plus the totals: "27 properties, 3 pages".

The Properties page uses this whenever nothing is typed in the search box. Search and filters still run in the browser on the full list, because the Arabic spelling rules live there. While a search is active, the browser pages the matches itself. You will see both in the demo: clear the search, choose 5 per page, and click Next. The browser's Network tab shows the `?page=1&size=5` request.

## 3. The contract

Everything is under `/api/v1/properties`, the same style as lab 14's `/api/v1/courses`.

| Method | Route | Request body | Success | Errors | Brief |
| --- | --- | --- | --- | --- | --- |
| GET | `/api/v1/properties?page=0&size=10` | – | 200, one page (below) | – | 4. all, paginated |
| GET | `/api/v1/properties/{id}` | – | 200, the property | 404 | 3. search by id |
| POST | `/api/v1/properties` | a property, without `id`, `createdAt`, `updatedAt` | 201, `Location: /api/v1/properties/{id}`, **the new property in the body** | 400 | 2. add |
| PUT | `/api/v1/properties/{id}` | a property, without `id`, `createdAt`, `updatedAt` | 200, **the updated property in the body** | 400, 404 | 5. update |
| DELETE | `/api/v1/properties/{id}` | – | 204, no body | 404 | not in the brief, but the app already deletes |

**Two differences from lab 14, on purpose.** POST and PUT return the property, where lab 14 returns no body. The app needs the new ID straight away to say "Property RP-0009 added" and to open its page. Also, lab 14's POST builds its `Location` as `/api/v1/{id}`, which is missing `courses`. Ours must be `/api/v1/properties/{id}`.

### One property, as JSON

The record's field names are the JSON names, and they must be exactly these. The 13 amenities are flat fields, and an empty optional field is `null`.

```json
{
  "id": 1,
  "city": "Riyadh",
  "district": "Al Malqa",
  "front": "North",
  "propertyType": "Villa",
  "sizeSqm": 620,
  "propertyAgeYears": 3,
  "bedrooms": 5,
  "bathrooms": 6,
  "livingRooms": 2,
  "kitchen": true, "garage": true, "driverRoom": false, "maidRoom": true,
  "furnished": false, "ac": true, "roof": false, "pool": true, "frontyard": true,
  "basement": false, "stairs": false, "elevator": false, "fireplace": false,
  "yearlyRentSar": 190000,
  "description": "Spacious family villa with a private pool.",
  "status": "Occupied",
  "tenantName": "Nora Al Harbi",
  "leaseStart": "2026-02-01",
  "leaseEnd": "2027-01-31",
  "createdAt": "2026-10-01T08:00:00Z",
  "updatedAt": "2026-10-01T08:00:00Z"
}
```

- **The ID is a number.** The app shows `1` as `RP-0001` and turns it back into `1` for the URL. The database issues it (`GENERATED BY DEFAULT AS IDENTITY`, as in lab 14) and **never reuses** a deleted number, which is what FR-DEL-06 asks for.
- **Dates** are `"YYYY-MM-DD"` (`LocalDate`). **Timestamps** are ISO instants (`Instant`). Spring Boot writes both as text, with no setup.

### One page, as JSON

Return `new PagedModel<>(page)` (`org.springframework.data.web.PagedModel`) from the controller. Do not return the `Page` itself: its JSON is not stable, and Spring logs a warning. The frontend reads exactly these names:

```json
{
  "content": [ { "id": 27, "...": "..." }, { "id": 26, "...": "..." } ],
  "page": { "size": 10, "number": 0, "totalElements": 27, "totalPages": 3 }
}
```

- Sort every page by `updatedAt`, newest first: `PageRequest.of(page, size, Sort.by("updatedAt").descending())`. That is the app's default order (FR-SRC-09).
- The app asks for `size=1000` once, to load everything for the Dashboard and the search. Do not cap `size` below 1000.

### Errors, as JSON

| Status | When | Body |
| --- | --- | --- |
| 400 | A field fails a check | `{ "errors": { "yearlyRentSar": "Yearly rent must be between 1,000 and 10,000,000 SAR." } }`, one entry per bad field |
| 400 | The JSON cannot be read, such as text where a number goes | `{ "message": "…" }` (any wording) |
| 404 | No property has the ID | `{ "message": "Property not found" }` |

The form shows each `errors` message beside its field, so **the field names and the messages must match the table in section 5 exactly**. One `@RestControllerAdvice` class builds all three bodies.

## 4. The table

One table, `property`. Spring Data JDBC turns `sizeSqm` into the column `size_sqm` by itself. The same SQL must run on H2 and on Postgres, and every type below works on both.

| Column | Type | Java field |
| --- | --- | --- |
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | `@Id Long id` |
| `city` | `VARCHAR(20) NOT NULL` | `String city` |
| `district` | `VARCHAR(60) NOT NULL` | `String district` |
| `front` | `VARCHAR(20)` | `String front` |
| `property_type` | `VARCHAR(10) NOT NULL` | `String propertyType` |
| `size_sqm` | `INTEGER NOT NULL` | `Integer sizeSqm` |
| `property_age_years` | `INTEGER NOT NULL` | `Integer propertyAgeYears` |
| `bedrooms`, `bathrooms`, `living_rooms` | `INTEGER NOT NULL` | `Integer` each |
| `kitchen`, `garage`, `driver_room`, `maid_room`, `furnished`, `ac`, `roof`, `pool`, `frontyard`, `basement`, `stairs`, `elevator`, `fireplace` | `BOOLEAN NOT NULL DEFAULT FALSE` | `boolean` each |
| `yearly_rent_sar` | `INTEGER NOT NULL` | `Integer yearlyRentSar` |
| `description` | `VARCHAR(2000)` | `String description` |
| `status` | `VARCHAR(20) NOT NULL` | `String status` |
| `tenant_name` | `VARCHAR(80)` | `String tenantName` |
| `lease_start`, `lease_end` | `DATE` | `LocalDate` each |
| `created_at`, `updated_at` | `TIMESTAMP WITH TIME ZONE NOT NULL` | `Instant` each |

- Use `Integer` for the numbers, so a missing one arrives as `null` and `@NotNull` can give its message. Use `boolean` for the amenities, so a missing one is simply false.
- `data.sql` inserts the starting properties with `DEFAULT` as the ID, as lab 14 does, **never a written number**. On Postgres a written ID does not move the counter on, so the next add would crash on a duplicate key. Inserted in order, the 8 hand-written properties in `frontend/src/test/portfolio.seed.json` keep their numbers 1 to 8.
- The 8 starting properties are enough for the demo: choose **5 per page** and they make 2 pages. Add more if you like; with 11 or more, even the default 10 per page shows a second page.
- Save `data.sql` as UTF-8, and set `spring.sql.init.encoding=UTF-8`: some districts and descriptions are Arabic.

## 5. The checks and their exact messages

These are the app's own checks (SRS Appendix C), copied from `frontend/src/constants/messages.js`. The form runs them before it sends anything, and the server runs them again, because anyone can call the API directly.

| Field | Rule | Message |
| --- | --- | --- |
| `city` | required; one of Riyadh, Jeddah, Dammam, Al Khobar | Choose a city. |
| `district` | required | Enter the district. |
| `district` | 2 to 60 characters | District must be 2 to 60 characters. |
| `front` | optional; one of North, South, East, West, Northeast, Northwest, Southeast, Southwest, Three streets, Four streets | (any) |
| `propertyType` | required; Villa or Duplex | Choose a property type. |
| `sizeSqm` | required | Enter the size in m² as a whole number. |
| `sizeSqm` | 20 to 100,000 | Size must be between 20 and 100,000 m². |
| `propertyAgeYears` | required; 0 to 100 | Age must be a whole number from 0 to 100 years. |
| `bedrooms` | required; 0 to 20 | Bedrooms must be a whole number from 0 to 20. |
| `bathrooms` | required; 0 to 20 | Bathrooms must be a whole number from 0 to 20. |
| `livingRooms` | required; 0 to 20 | Living rooms must be a whole number from 0 to 20. |
| `yearlyRentSar` | required | Enter the yearly rent in SAR as a whole number. |
| `yearlyRentSar` | 1,000 to 10,000,000 | Yearly rent must be between 1,000 and 10,000,000 SAR. |
| `description` | at most 2,000 characters | Description must be 2,000 characters or fewer. |
| `status` | required; Vacant, Occupied or Under maintenance | Choose a status. |
| `tenantName` | 2 to 80 characters | Tenant name must be 2 to 80 characters. |
| `tenantName` | required when `status` is Occupied **(Service)** | Enter the tenant's name for an occupied property. |
| `leaseEnd` | after `leaseStart`, when both are given **(Service)** | Lease end must be after lease start. |

- One-field rules are Bean Validation annotations on the record, as in lab 14's `Course`: `@NotNull`, `@NotBlank`, `@Size`, `@Min`, `@Max`, and `@Pattern(regexp = "Riyadh|Jeddah|Dammam|Al Khobar")` for a fixed list. Put the message in each one: `message = "Choose a city."`.
- Rules that compare two fields go in the **Service**. It throws an `InvalidPropertyException` that carries the field name and the message, and the `@RestControllerAdvice` turns that into the same 400 body.
- **When the status is not Occupied, the Service clears `tenantName`, `leaseStart` and `leaseEnd`** (sets them to `null`) before saving (FR-UPD-07).
- When two rules fail on one field, such as an empty district, either message is fine.

## 7. The database: Supabase, with H2 as the fallback

Supabase was dropped on 11 November 2026 and brought back on 12 November 2026, agreed by the team. The brief does not ask for a database, so Supabase is the extra the demo shows: a property added in the app is still there after Spring restarts. H2 stays the default, so the tests, a fresh laptop and a bad network all still work with no setup.

| | H2 (default profile) | Supabase (`supabase` profile) |
| --- | --- | --- |
| Where the data lives | In memory, inside Spring | Postgres in the cloud |
| `schema.sql` and `data.sql` | Run by Spring at every start | Run once, by hand, in step 2 below |
| After a restart | Back to the 8 starting properties | Everything kept |
| Needs | Nothing | `backend/.env` and a network that allows port 5432 |
| Used by the tests | Yes | Never |

### Setting it up (Person A)

1. Create a free project at [supabase.com](https://supabase.com). Keep the database password private: **this repository is public**.
2. In the **SQL Editor**, run `schema.sql`, then `data.sql`, then this one line, which belongs to Supabase only:
   `ALTER TABLE property ENABLE ROW LEVEL SECURITY;`
   It closes Supabase's own public data API to the table. Spring is not affected, because it connects as the table's owner.
3. Under **Connect**, copy the **Session pooler** connection details. That one works on any network. The "Direct connection" needs IPv6, which many networks lack.
4. Each person creates `backend/.env`. The repository's `.gitignore` already keeps every `.env` out of git. It holds three lines:
   ```
   DB_URL=jdbc:postgresql://<pooler host>:5432/postgres?sslmode=require
   DB_USER=postgres.<project ref>
   DB_PASSWORD=<the password>
   ```
5. `application.properties` imports that file with `spring.config.import=optional:file:.env[.properties]`. `application-supabase.properties` sets `spring.datasource.url`, `username` and `password` to `${DB_URL}`, `${DB_USER}` and `${DB_PASSWORD}`.
6. **Free projects pause after a week without use.** Open the Supabase dashboard on 13 November, and again on the morning of 14 November, to be sure it is awake.
7. **Never point the tests at Supabase.** `mvnw.cmd test` runs on the default profile, so the tests use H2 and mocks and never change the shared data.

On H2, Spring runs `schema.sql` and `data.sql` itself at every start, because H2 is an embedded database. On Supabase it never runs them: the table was made once in step 2, and the data stays between restarts.

### Looking at the data

- **On Supabase,** open the project's **Table Editor**, or run SQL in the **SQL Editor**.
- **On H2,** turn on the H2 console:
  - Add `org.springframework.boot:spring-boot-h2console` to `pom.xml`. Spring Boot 4 moved the console into this module, and without it `/h2-console` answers 404.
  - In `application.properties`, set `spring.h2.console.enabled=true`, and `spring.datasource.url=jdbc:h2:mem:darscope` so the address is always the same. The `supabase` profile overrides that URL.
  - Open <http://localhost:8080/h2-console>. Log in with that JDBC URL, the user `sa` and an empty password. Then run `SELECT * FROM property;`.
  - The console and the app share one database. A row you change in the console shows in the app after a page reload.

## 9. Tests (brief requirement 6)

"Test all the backend" means every method of the Service and every route of the Controller, including the failure paths. Name each test after what it proves.

**`PropertyServiceTest`** uses `@ExtendWith(MockitoExtension.class)`, `@Mock PropertyRepository`, `@InjectMocks PropertyService`, and no Spring context.

- `getById` returns the property, and throws `ObjectNotFoundException` for an unknown ID.
- `create`:
  - saves with no ID and sets `createdAt` equal to `updatedAt`. Use an `ArgumentCaptor` to read what was passed to `save`.
  - clears tenant and lease fields when the status is not Occupied;
  - rejects Occupied without a tenant name, and a lease end on or before the start.
- `update`:
  - keeps the ID and `createdAt`, and sets a new `updatedAt`;
  - throws for an unknown ID and never calls `save` (`verify(repository, never()).save(any())`).
- `delete` calls `deleteById`, and throws for an unknown ID.
- `getPage` passes the page request through to the repository.

**`PropertyControllerTest`** uses `@WebMvcTest(PropertyController.class)`, `@MockitoBean PropertyService`, and `MockMvc`. For every route, test each status in the contract (200, 201, 204, 400, 404), and check the JSON with `jsonPath`. In particular:

- `"$.page.totalElements"` on the list;
- the `Location` header on POST;
- `"$.errors.yearlyRentSar"` holding the exact message when the rent is 500;
- `"$.message"` being `Property not found` on a 404.

**Spring Boot 4 traps** (lab 14 is already on Boot 4):

- `@MockBean` no longer exists. Use `@MockitoBean` (`org.springframework.test.context.bean.override.mockito`).
- `@WebMvcTest` lives in `org.springframework.boot.webmvc.test.autoconfigure`, and needs the `spring-boot-starter-webmvc-test` dependency that lab 14 has.
- Boot 4 uses Jackson 3, whose package is `tools.jackson`, not `com.fasterxml.jackson`. In tests, the simplest request body is a Java text block (`"""{ "city": "Riyadh", ... }"""`) instead of an `ObjectMapper`.
- This laptop has JDK 26. The project targets 21, like lab 14. If Mockito fails with an error about the Java version, install JDK 21 and point the project at it.

## What changed on the frontend for Part 2

So that the frontend owner knows what to review:

- `frontend/vite.config.js` forwards `/api` to `localhost:8080`.
- `frontend/src/services/propertyService.js` now calls the routes above. Two helpers do the translating:
  - `fromServer` turns `id: 7` into `RP-0007`, the flat amenities into the app's `amenities` object, and `null` into empty text;
  - `toServer` turns them back.

  It also checks the values before sending, adds `listPage(page, perPage)`, and turns a 400 into field errors, a 404 into "Property not found", and a dead server into a clear message.
- The Properties page has Previous and Next and a "Per page" choice of 5, 10, 25 or 50, with 10 as the default (FR-LST-10 plus 5, so a small portfolio still has pages). With no search, each page comes from the server (`hooks/useServerPage.js`). With a search, the browser pages the matches.
- Undo delete and "Reset demo data" were removed: nothing on screen used them, and resetting a shared database is risky. `npm run prepare-data` was removed too: its script was never written, and the starting data now lives in `data.sql`.
- The footer and About page no longer say that changes vanish on reload.
- Tests never reach a server. `frontend/src/test/fakePropertyService.js` stands in for the real service in every test except the service's own, which replaces `fetch` with a stub.
